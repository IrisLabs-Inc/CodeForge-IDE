What you're building on: Nukepad is a Java Swing desktop editor (Maven, JDK 11+) built on the TEDitor base, with RSyntaxTextArea for editing, a FileTree/Categories/Search sidebar, a Git panel wrapping the git CLI, an interactive terminal, a Problems panel fed by compiler output, and — as of v1.0 beta — a plugin manager scripted in Java. It already has a Compile/Run dispatch that branches by file type (javac/g++/gcc for compile, java/python3/node for run). That dispatch pattern and the plugin manager are your two best extension points — you don't want to hand-roll Android/ESP/Arduino toolchains, you want to wrap the real ones (arduino-cli, ESP-IDF, Android SDK/Gradle) the same way the Git panel wraps git.

Strategic call: plugins, not core forks

Given v1.0 already ships a plugin system, build Android/ESP/Arduino support as three separate plugins rather than hard-forking core classes. That keeps upstream merges possible, lets users install only what they need, and matches the project's own direction.

Phase 0 — Shared infrastructure (do this first, all three depend on it) [DONE]
Project-type detection: scan the opened root folder for markers — .ino file → Arduino/ESP-Arduino; CMakeLists.txt + idf_component.yml → ESP-IDF; build.gradle/build.gradle.kts + AndroidManifest.xml → Android. Surface this as a badge next to the project in the Opened Projects panel.
Toolchain settings panel: paths to arduino-cli binary, ESP-IDF install (IDF_PATH), Android SDK root, JDK for Gradle. Store like ThemeManager does — a config file in the user's home dir.
Device/Port manager panel: one unified panel listing serial ports (for Arduino/ESP) and ADB devices (for Android), refreshed on demand. This is your single biggest UX win — it's the thing all three domains need and none of them have yet.
Serial library: pull in jSerialComm via Maven (pure Java, no native build step — fits your existing pom.xml-driven dependency model far better than RXTX). This powers both flashing progress and the Serial Monitor.
Extend the Run/Compile dispatcher: add cases that hand off to a new BuildRunner interface, implemented per plugin (ArduinoCliRunner, EspIdfRunner, GradleRunner), same shape as the existing Git Runner.
Extend the Problems panel to parse output from these new toolchains, not just javac/gcc.
Phase 1 — Arduino support [DONE]
- ArduinoCliRunner wraps arduino-cli: compile, upload, board list, core install, lib install/search
- New Arduino Sketch template (setup()/loop() boilerplate)
- Arduino popup on ActivityBar with Board Manager, Library Manager, Compile, Upload, Serial Monitor
- Serial Monitor panel in bottom tabs (jSerialComm, port selector, baud rate, connect/disconnect)
- Library Manager panel (search + install Arduino libraries)
- Board Manager panel (install/manage cores: avr, esp32, esp8266, rp2040, etc.)
- FQBN persisted per-sketch in .arduino-cli.fqbn file

Phase 2 — ESP32 / ESP8266 support [DONE]

Two viable paths — both are now supported:

Arduino-framework route (reuses Phase 1): install ESP32/ESP8266 board package via Board Manager (arduino-cli core install esp32:esp32), then everything from Phase 1 works.
ESP-IDF route (native CMake projects):
- EspIdfBuildRunner wraps idf.py (build, flash, monitor, menuconfig, fullclean)
- ESP-IDF project template generator (CMakeLists.txt + main/ skeleton + idf_component.yml + sdkconfig.defaults)
- ESP-IDF popup on ActivityBar with Build, Build & Flash, Serial Monitor, Menuconfig, Full Clean, New Project
- CMake/ninja error parsing into Problems panel
Phase 3 — Android support [DONE]
- AndroidBuildRunner wraps gradlew (assembleDebug, installDebug, deploy + launch)
- Android popup on ActivityBar with Build, Build & Deploy, Logcat, Device Manager
- Logcat panel streams adb logcat in bottom tabs (device selector, tag filter, start/stop)
- SVG icons fetched from material-design-icons (android, play, hammer, console, phone, bug)
- Syntax highlighting added for .kt (Kotlin), .gradle/.groovy (Groovy), .yaml/.yml (YAML)
- Device selector from DeviceManagerPanel's ADB list
Skip a live XML layout preview initially — it's a large rabbit hole (needs a layout renderer) and isn't essential to get building/running/debugging working.
Suggested build order
Phase 0 (device manager + settings panel — nothing else works without it)
Arduino (cheapest full loop: compile → upload → serial monitor)
ESP32 via the Arduino path (near-free once Arduino works)
Android (biggest scope — do it last so the plugin architecture is already proven)
ESP-IDF native path (nice-to-have, lower priority than the above)

Cleanup done:
- Removed generic Compile/Run buttons from ActivityBar (replaced by platform-specific popups)
- Removed JavaScript/TypeScript file templates (not used in robotics)
- Removed JS/TS/Python from generic Compile fallback (interpreted languages)
- Removed JS/TS from generic Run fallback

A few things worth flagging as you go: Nukepad is GPL-3.0, which sets the license for your fork's plugins too if they're not cleanly separated processes; and all three toolchains (arduino-cli, ESP-IDF, Android SDK) have real path/version differences across Windows/Mac/Linux, so the settings panel and clear error messages when a tool isn't found will save you the most support pain.
